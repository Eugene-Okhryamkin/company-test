# ADR-006: AI-поиск — LLM переводит запрос в структурированный фильтр, фильтрует клиент

- **Статус:** принято
- **Дата:** 2026-09-15
- **Этап:** 04 BONUS

## Контекст

Требование: строка поиска принимает естественный язык («команды с эффективностью ниже 60», «топ-3 отдела по бюджету»), ответ — структурированный фильтр, который применяется на клиенте; fallback — текстовый поиск.

Ограничения и риски:

- ключ LLM-провайдера нельзя отдавать в браузер;
- ответ модели недетерминирован и может не совпасть с ожидаемой формой;
- LLM стоит денег и отвечает сотни миллисекунд — секунды; запрос на каждое нажатие клавиши неприемлем;
- данные обновляются в реальном времени, выборка должна оставаться актуальной;
- провайдер может быть не настроен (нет ключа) или недоступен — поиск всё равно должен работать.

Выбор провайдера: **OpenAI API** (решение заказчика), Responses API со Structured Outputs.

## Решение

1. **Backend-прокси.** `POST /api/search/interpret` принимает `{ query }` и возвращает `{ filter }`. Ключ `OPENAI_API_KEY` есть только на сервере (`.env` → docker-compose). `GET /api/search/status` сообщает клиенту `aiEnabled`.
2. **Structured Outputs, strict.** `OpenAiResponsesClient` вызывает `POST /v1/responses` с `text.format: { type: "json_schema", strict: true, schema: SEARCH_FILTER_JSON_SCHEMA }` и `store: false`. Модель не может вернуть поля вне схемы; отсутствие условия — `null`/`[]`.
3. **Модель только переводит, данные не отправляются.** В промпте описаны столбцы, уровни, единицы и правила («5 млн», «топ N», «высокая эффективность»). Сами узлы в LLM не уходят: это дешевле, быстрее и не раскрывает данные.
4. **Защитная валидация на двух сторонах.** Backend `parseSearchFilter` проверяет и нормализует ответ (обмен `min > max`, клэмп 0–100, trim), нарушение → `502`. Клиент валидирует ответ zod-схемой.
5. **Фильтр применяет клиент** (`applySearchFilter`) к строкам таблицы, над агрегатами поддерева. Фильтр хранится как состояние, поэтому live-патчи сразу пересчитывают выборку без новых запросов к LLM.
6. **Явный запуск AI.** Ввод по-прежнему фильтрует по названию в реальном времени (дебаунс 250 мс). Запрос к LLM уходит только по Enter или кнопке «AI-поиск». Понятые условия показываются чипами, «Сбросить» и любое редактирование возвращают текстовый режим. Повтор того же запроса не отправляется, ответ на устаревший запрос отбрасывается.
7. **Fallback.** Нет ключа → кнопки нет, поле работает как текстовый поиск. Ошибка (`502`/`503`, сеть, ответ не по схеме) → остаётся текстовый поиск по той же строке и сообщение «AI-поиск недоступен — показаны результаты поиска по названию».
8. **Архитектура backend.** Порт `LlmClient` (адаптер `OpenAiResponsesClient` на `fetch`, внедряемом через DI) → `AiSearchService` (бизнес-правила, ошибки предметной области) → `SearchController` (HTTP-статусы). Модель и таймаут настраиваются через `OPENAI_MODEL`, `OPENAI_BASE_URL`, `AI_SEARCH_TIMEOUT_MS`.

## Альтернативы

| Вариант | Почему нет |
|---|---|
| Вызывать OpenAI прямо из браузера | Ключ оказывается в бандле или сетевых запросах |
| JSON mode / «верни JSON» в промпте без схемы | Форма не гарантирована: лишние или пропущенные поля, строки вместо чисел |
| Function calling (tools) | Для одного структурированного ответа избыточно; Structured Outputs в `text.format` проще и даёт ту же гарантию схемы |
| Фильтрация на сервере (LLM или SQL возвращает id узлов) | Требование задания — фильтр на клиенте; выборка устаревала бы при live-патчах; пришлось бы дублировать агрегацию на backend |
| Отправлять данные в LLM и просить отобрать узлы | Дорого (токены растут с размером оргструктуры), медленно, возможны галлюцинации и утечка данных |
| Семантический поиск через embeddings | Хорош для «похожих названий», но не понимает числовые условия, сортировку и «топ N» |
| Правила/регулярные выражения без LLM | Хрупко на свободных формулировках; как основная реализация не отвечает заданию |
| AI-запрос автоматически по дебаунсу | Платный вызов на каждую паузу в наборе и «прыгающая» таблица; явный Enter предсказуем |
| Официальный SDK `openai` | Лишняя зависимость ради одного запроса; `fetch` проще подменять в тестах |

## Последствия

- **Плюсы:** ключ не покидает сервер; контракт фильтра проверяется трижды (схема OpenAI, backend, zod); выборка живая при live-обновлениях; приложение полностью работает без ключа; логику и транспорт легко тестировать (LLM подменяется в DI, `fetch` — в клиенте OpenAI).
- **Минусы:** качество понимания зависит от модели и промпта (не покрывается unit-тестами, нужны ручные проверки или eval-набор); задержка ответа LLM; расходы на API.
- **Не сделано (точки расширения):** rate limiting и кэш одинаковых запросов на backend; eval-набор «запрос → ожидаемый фильтр» для регрессий промпта; стриминг и отмена запроса при сбросе.
