# ADR-002: Runtime-валидация ответа API через zod

- **Статус:** принято
- **Дата:** 2026-09-15
- **Этап:** 01 FOUNDATION

## Контекст

По заданию схема ответа API проверяется на клиенте, а невалидный ответ считается ошибкой. Типы TypeScript исчезают после компиляции и не защищают от реального ответа сервера. Кроме формы полей, для построения дерева нужна **целостность** плоского списка: уникальные `id`, существующие `parentId`, отсутствие циклов. Иначе дерево построится с потерянными узлами или зациклится.

## Решение

- Контракт описан zod-схемой в `client/src/entities/org-node/model/org-node.schema.ts`. Тип `OrgNode` выводится из неё (`z.infer`), так что типы и runtime-проверка не расходятся.
- Поля: `id`, `name` — непустые строки; `parentId` — строка или `null`; `headcount` — целое ≥ 0; `budget` ≥ 0; `performance` в диапазоне 0–100; `updatedAt` — ISO 8601.
- Целостность проверяется через `superRefine` на массиве за O(n): дубликаты, неизвестные родители, циклы.
- Поля вне контракта отбрасываются.
- `getJson` превращает любой сбой в `ApiError` с `kind`: `network`, `http`, `parse` или `validation`. Для пользователя выбирается понятное сообщение (`getErrorMessage`), технические детали остаются в `error.message` и `cause`.

## Альтернативы

| Вариант | Почему не выбран |
|---|---|
| Ручные type guards | Много кода, легко разойтись с типами, нет подробных путей ошибок |
| valibot | Меньше бандл, но для одной схемы разница несущественна; у zod шире распространённость и лучше выразительность `superRefine` |
| Проверять только на backend | Задание явно требует проверки на клиенте; клиент не должен доверять сети |

## Последствия

- ➕ Одна схема даёт и тип, и проверку; невалидный ответ не доходит до UI и не ломает построение дерева.
- ➕ `buildOrgTree` может полагаться на валидный лес и оставаться простым.
- ➖ Проверка стоит O(n) на каждый ответ. Для десятков и сотен узлов это пренебрежимо мало.
- ➖ Зависимость от zod в бандле.
