# ADR-005: Live-обновления через WebSocket с версионированием данных

- **Статус:** принято
- **Дата:** 2026-09-15
- **Этап:** 03 POLISH

## Контекст

Требования задания:

- сервер поддерживает обновления в реальном времени; клиент использует WebSocket, SSE или эффективный поллинг (с учётом частоты изменений, backoff и минимизации запросов);
- патч применяется без полного рефетча; обновлённые ячейки подсвечиваются и гаснут за ~1,5 с;
- агрегаты пересчитываются только для затронутого узла и его предков;
- индикатор соединения в шапке, экспоненциальный backoff при обрыве.

Главный риск любой push-схемы — рассинхронизация. Если клиент пропустит патч (обрыв, snapshot загрузился «между» патчами, рестарт сервера), его данные тихо разойдутся с серверными.

## Решение

1. **Транспорт — WebSocket** (`ws` на backend, нативный `WebSocket` в браузере) на пути `/api/live` того же origin.
2. **Монотонная версия данных.** Каждый применённый пакет изменений на сервере увеличивает `version` на 1. Версия приходит:
   - в `GET /api/org-tree` — заголовок `X-Data-Version` (контракт тела остаётся плоским массивом);
   - в каждом сообщении канала: `hello`, `patch`, `heartbeat`.
3. **Клиент применяет патч, только если `version = текущая + 1`.** Более старые версии игнорируются, пропуск (или смена версии в `hello`/`heartbeat`, например после рестарта) вызывает **один** повторный `GET` снапшота. В нормальном режиме запросов нет.
4. **Патч содержит только метрики** (`headcount`, `budget`, `performance`, `updatedAt`), по одному полному набору на узел. Структура в live не меняется, поэтому модель можно обновлять инкрементально, а применение идемпотентно.
5. **Применение в кэш TanStack Query** (`setQueryData`) с собственным `structuralSharing`: патченые массивы сохраняются как есть, обычные ответы проходят через `replaceEqualDeep`. Модель дерева пересчитывается только на пути «узел → корень» функцией, общей с полной агрегацией (`computeUnitStats`), и регистрируется для нового массива, поэтому `select` не запускает полный пересчёт.
6. **Heartbeat** = ws-ping (сервер отключает неответивших) + прикладное сообщение с версией. Браузер не видит ping-кадры, поэтому клиентский watchdog закрывает соединение, если сообщений нет дольше `2,5 × heartbeatIntervalMs`, и попытку подключения, не открывшуюся за 10 с.
7. **Переподключение** — `ReconnectingSocket`: backoff 500 мс × 2^n до 30 с с джиттером ±20 %, сброс после успеха, пауза при `offline` и мгновенная попытка при `online`, ручной «Переподключиться» из индикатора.
8. **Архитектура backend.** Бизнес-логика изменений — в `OrgTreeService.applyChanges` (атомарная валидация пакета, версия, публикация). Транспорт — `LiveUpdatesGateway`, связанный с сервисом через in-process `OrgTreeChangeBus`. Источник изменений — `LiveUpdateSimulator` (mock).

## Альтернативы

| Вариант | Почему не выбран |
|---|---|
| **SSE** (`EventSource`) | Односторонний канал подходит по смыслу и умеет переподключаться сам, но задание явно просит «контракт WebSocket-патча»; встроенный reconnect EventSource не даёт управлять backoff и статусом так, как нужно для индикатора |
| **Поллинг с ETag** | Даже с `304` это запрос каждые N секунд на клиента; задержка обновлений равна периоду опроса; «пересчёт только затронутых узлов» потребовал бы вычислять diff на клиенте |
| **Патчи без версий** | Нельзя обнаружить пропуск: после короткого обрыва или загрузки снапшота «между» патчами данные расходятся без признаков |
| **Всегда рефетч при любом событии** | Нарушает требование «без полного рефетча» и нагружает сервер при каждом изменении |
| **Готовые клиенты** (socket.io, reconnecting-websocket) | Добавляют вес и собственный протокол; нужная логика (backoff, watchdog, online/offline, статус) укладывается в ~200 строк и полностью покрыта тестами |
| **Дельты метрик в патче** (`+1`, `−0,5`) | Не идемпотентны: повторная доставка или применение поверх нового снапшота искажает значения |

## Последствия

- ➕ В нормальном режиме — ноль HTTP-запросов после первой загрузки; обновления приходят сразу.
- ➕ Любая рассинхронизация самоустраняется одним запросом снапшота; клиент никогда не показывает «тихо устаревшие» данные.
- ➕ Инкрементальная модель побитово совпадает с полной (тест сверяет после 200 случайных патчей); вне пути «узел → корень» ссылки сохраняются, мемоизированные строки не перерисовываются.
- ➕ Индикатор честно отражает состояние: подключение, ожидание с обратным отсчётом, офлайн.
- ➖ Версия живёт в памяти процесса и сбрасывается при рестарте — клиент это переживает (resync), но при нескольких инстансах backend понадобится общий счётчик и внешняя шина (Redis Pub/Sub).
- ➖ Структурные изменения (новые узлы, перемещение, переименование) в live не поддерживаются; для них потребуется отдельный тип сообщения или resync.
- ➖ Долгоживущие соединения требуют настройки прокси (`Upgrade`, таймауты) — сделано в nginx и Vite proxy.
