# ADR-004: Агрегация поддеревьев и её мемоизация

- **Статус:** принято
- **Дата:** 2026-09-15
- **Этап:** 02 CORE

## Контекст

Требования задания к таблице:

- суммарные показатели включают данные узла и всех его потомков;
- средняя эффективность взвешена по headcount;
- агрегация считается один раз после загрузки данных и мемоизируется.

Агрегаты нужны дереву и таблице одновременно. На этапе 03 live-патчи должны пересчитывать только затронутый узел и его предков.

## Решение

1. **Чистая функция** `aggregateOrgTree(forest)` за O(n): итеративный обход в обратном pre-order, без рекурсии.
2. **Хранятся промежуточные суммы:** `performanceWeight = Σ performance·headcount`, `performanceSum`, `nodeCount`. Все показатели аддитивны, поэтому на этапе 03 предков можно обновлять разницей между старым и новым значением.
3. **Если в поддереве нет сотрудников** (Σ headcount = 0), берётся простое среднее вместо `NaN`.
4. **Одна модель на всё приложение:** `buildOrgTreeModel` собирает лес, индекс, агрегаты и строки таблицы.
5. **Мемоизация в двух слоях:**
   - TanStack Query `structuralSharing` сохраняет ссылку на `data`, пока ответ не изменился;
   - `getOrgTreeModel` кэширует модель в `WeakMap` по этой ссылке и используется как `select`.

   Итог: расчёт выполняется один раз на каждое реальное изменение данных, сколько бы компонентов ни читали модель.

## Альтернативы

| Вариант | Почему не выбран |
|---|---|
| `useMemo` в каждом компоненте | Дерево и таблица считали бы агрегаты каждый сам: два расчёта, и при смене раскладки пересчёт повторяется при каждом монтировании |
| Только `select` без `WeakMap` | TanStack мемоизирует `select` для каждого наблюдателя отдельно; при двух `useQuery` расчёт выполнится дважды (тест это проверяет) |
| Агрегаты на backend | Задание требует агрегации на клиенте; к тому же live-патчи этапа 03 всё равно придётся применять на клиенте |
| Рекурсивный обход | Проще читается, но упирается в размер стека на глубоких деревьях |
| Хранить только итоговые значения | Для инкрементального обновления на этапе 03 пришлось бы заново обходить всё поддерево |

## Последствия

- ➕ Один проход O(n) на изменение данных; дерево и таблица используют один объект.
- ➕ Модель готова к инкрементальному пересчёту (этап 03).
- ➕ `WeakMap` не создаёт утечек: устаревшие модели освобождаются вместе с данными.
- ➖ Мемоизация опирается на неизменяемость данных. Данные из кэша нельзя мутировать, их можно только заменять (так и работает TanStack Query).
- ➖ Для 40–1000 узлов инкрементальность пока не нужна, но структура данных под неё уже заложена.
