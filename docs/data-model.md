# Модель данных

> Контракт API, дерево, алгоритм агрегации (этап 02), контракт WebSocket-патча и инкрементальный пересчёт (этап 03).

## 1. Контракт API

`GET /api/org-tree` возвращает **плоский массив** узлов. Иерархия задаётся ссылкой на родителя. Заголовок `X-Data-Version` содержит версию данных, по которой клиент выравнивает snapshot с live-патчами (раздел 4).

```ts
interface OrgNode {
  id: string            // уникальный, непустой
  name: string          // непустой
  parentId: string | null // null — корень (дивизион)
  headcount: number     // целое ≥ 0 — сотрудники самого узла
  budget: number        // ≥ 0, руб. — бюджет самого узла
  performance: number   // 0–100
  updatedAt: string     // ISO 8601, UTC
}
```

`headcount` и `budget` относятся **только к самому узлу**, без потомков. Суммы по подразделениям считает клиент (раздел 3).

Контракт проверяется дважды:

| Где | Чем | Что гарантирует |
|---|---|---|
| Backend | `services/org-tree.validator.ts` | Сервер не отдаёт невалидные данные (иначе `500`) |
| Client | zod-схема `entities/org-node/model/org-node.schema.ts` | Клиент не доверяет сети: невалидный ответ превращается в ошибку и до UI не доходит |

Инварианты, общие для обеих сторон: уникальные `id`, существующий `parentId`, отсутствие циклов, диапазоны числовых полей, валидная дата. Благодаря им плоский список всегда образует **лес** (одно или несколько деревьев).

Seed-данные: 4 дивизиона → 12 отделов → 28 команд, всего 44 узла и 3 уровня.

## 2. Дерево

### Структуры

```ts
interface OrgTreeNode {
  node: OrgNode          // исходный объект из ответа (та же ссылка)
  level: number          // 1 — дивизион, 2 — отдел, 3 — команда, …
  children: OrgTreeNode[]
}

interface OrgTreeModel {
  forest: OrgTreeNode[]                  // корни в порядке ответа
  byId: Map<string, OrgTreeNode>         // быстрый доступ к узлу
  stats: Map<string, OrgUnitStats>       // агрегаты по поддеревьям (раздел 3)
  rows: OrgTableRow[]                    // строки таблицы в иерархическом порядке
}

interface OrgTableRow {
  id: string
  name: string
  level: number
  totalHeadcount: number
  totalBudget: number
  avgPerformance: number
  order: number          // позиция при обходе в глубину: порядок по умолчанию и разрешение равенства при сортировке
}
```

### Построение: `buildOrgTree(nodes)` — O(n)

1. **Индекс.** Для каждого узла создаётся `OrgTreeNode` в `Map<id, OrgTreeNode>`.
2. **Связывание.** Каждый узел добавляется в `children` родителя или, если `parentId === null`, в список корней. Порядок детей совпадает с порядком в ответе, поэтому не важно, идёт ли родитель в массиве раньше детей.
3. **Уровни.** Итеративный обход в глубину от корней со стеком: `level = level(parent) + 1`.

Рекурсия не используется, поэтому глубина дерева ограничена только памятью (тест на 20 000 уровней).

### Модель: `buildOrgTreeModel(nodes)`

`buildOrgTree` → `aggregateOrgTree` → один обход в глубину с сохранением порядка детей, который заполняет `byId` и `rows`.

### Мемоизация

```ts
const modelCache = new WeakMap<readonly OrgNode[], OrgTreeModel>()
getOrgTreeModel(nodes) // один расчёт на каждую ссылку на массив
```

Хук `useOrgTreeModelQuery` использует `getOrgTreeModel` как `select` в TanStack Query. Structural sharing сохраняет ссылку на `data`, пока данные не изменились, поэтому модель:

- считается **один раз после загрузки**;
- **не пересчитывается** при фоновой перепроверке с тем же ответом;
- **общая** для дерева и таблицы (и любых других потребителей).

`WeakMap` не удерживает старые массивы: после замены данных прежняя модель освобождается сборщиком мусора.

## 3. Агрегация

### Показатели

Для узла `v` и его поддерева `T(v)` (сам узел и все потомки):

| Показатель | Формула |
|---|---|
| `totalHeadcount(v)` | Σ `headcount(u)`, u ∈ T(v) |
| `totalBudget(v)` | Σ `budget(u)`, u ∈ T(v) |
| `avgPerformance(v)` | Σ(`performance(u)` · `headcount(u)`) / `totalHeadcount(v)` |
| — если `totalHeadcount(v) = 0` | Σ `performance(u)` / \|T(v)\| (простое среднее) |

**Почему среднее взвешено по headcount.** Эффективность подразделения — это эффективность его сотрудников. Команда из 99 человек с показателем 0 и руководитель с показателем 100 дают 1, а не 50. Узлы без сотрудников в среднее не входят.

**Почему есть запасной вариант.** Если в поддереве нет ни одного сотрудника, взвешенное среднее не определено (0/0). Простое среднее даёт осмысленное значение вместо `NaN`.

### Промежуточные значения

```ts
interface OrgUnitStats {
  totalHeadcount: number
  totalBudget: number
  avgPerformance: number
  performanceWeight: number // Σ performance · headcount
  performanceSum: number    // Σ performance
  nodeCount: number         // |T(v)|
}
```

Хранятся не только итоговые значения, но и **суммы**, из которых они получаются. Все показатели аддитивны, поэтому агрегат родителя равен собственным значениям плюс агрегаты детей. Это позволит на этапе 03 пересчитывать только изменённый узел и его предков: вычесть старый вклад, прибавить новый, без обхода всего дерева.

### Алгоритм: `aggregateOrgTree(forest)` — O(n) по времени и памяти

```
preOrder ← обход в глубину со стеком (родитель раньше потомков)
для v в обратном порядке preOrder:            # дети обрабатываются раньше родителя
    s ← собственные значения v, nodeCount = 1
    для каждого ребёнка c:
        s += stats[c]                          # headcount, budget, performanceWeight, performanceSum, nodeCount
    avg ← s.totalHeadcount > 0 ? s.performanceWeight / s.totalHeadcount
                               : s.performanceSum / s.nodeCount
    stats[v] ← { …s, avgPerformance: avg }
```

Каждый узел и каждое ребро обрабатываются один раз. Рекурсии нет.

### Пример (тестовые данные)

| Узел | Собственные: headcount, performance | Всего сотрудников | Взвешенная эффективность |
|---|---|---|---|
| Core API | 9, 40 | 9 | 40 |
| Платформа | 3, 65 | 3 + 9 = 12 | (3·65 + 9·40) / 12 = **46,25** |
| Дизайн | 5, 90 | 5 | 90 |
| Технологии | 4, 82 | 4 + 12 + 5 = 21 | (4·82 + 555 + 5·90) / 21 = **63,48** |

Тесты: `entities/org-node/lib/__tests__/aggregate-org-tree.test.ts` (формулы, случаи с нулевым headcount, глубина 20 000) и `org-tree-model.test.ts` (строки, мемоизация, предки).

## 4. WebSocket-патч (live-обновления)

### Канал

| | |
|---|---|
| URL | `ws(s)://<origin>/api/live` — тот же origin, что и у приложения (nginx / Vite proxy) |
| Направление | Только сервер → клиент; сообщения клиента игнорируются |
| Формат | JSON, одно сообщение на кадр |
| Версия данных | Целое `version ≥ 0`, на сервере растёт на 1 с каждым применённым пакетом изменений. Сбрасывается при рестарте сервера |

### Сообщения

```ts
type LiveMessage =
  | { type: 'hello'; version: number; heartbeatIntervalMs: number } // сразу после подключения
  | { type: 'heartbeat'; version: number }                          // каждые heartbeatIntervalMs
  | { type: 'patch'; version: number; nodes: OrgNodePatch[] }       // каждое изменение данных

interface OrgNodePatch {
  id: string          // существующий узел
  headcount: number   // целое ≥ 0
  budget: number      // ≥ 0
  performance: number // 0–100
  updatedAt: string   // ISO 8601, UTC
}
```

Пример:

```json
{ "type": "patch", "version": 42, "nodes": [
  { "id": "d1-1", "headcount": 4, "budget": 6300000, "performance": 86.5, "updatedAt": "2026-09-15T10:00:00.000Z" }
] }
```

Правила:

- **В патче только метрики.** `name` и `parentId` в реальном времени не меняются, поэтому структура дерева в live-режиме постоянна.
- **Каждый узел в патче передаётся со всеми тремя метриками.** Применение идемпотентно и не зависит от порядка полей.
- **Один патч — одна версия.** Несколько узлов, изменённых за один такт, приходят одним сообщением (`version` +1).
- **Heartbeat** — это ws-ping (сервер разрывает соединения, которые не ответили) плюс прикладное сообщение с версией. Браузер не видит ping-кадры, поэтому ему нужно прикладное сообщение, чтобы заметить «тихое» соединение и пропущенные версии.
- **Все сообщения проверяются на клиенте** zod-схемой (`entities/org-node/live/live-message.schema.ts`). Невалидное сообщение игнорируется.

### Синхронизация snapshot ↔ патчи

Версия snapshot хранится рядом с данными кэша: `WeakMap` по ссылке на массив, заполняется из `X-Data-Version` и из версий патчей.

| Событие на клиенте | Условие | Действие |
|---|---|---|
| `patch` | нет snapshot (идёт первая загрузка) | игнорировать |
| `patch` | `version ≤ текущей` | игнорировать (уже учтено) |
| `patch` | `version = текущая + 1` | **применить в кэше без запроса** |
| `patch` | `version > текущая + 1` или неизвестный `id` | один повторный `GET /api/org-tree` (resync) |
| `hello` / `heartbeat` | `version = текущей` | отметить данные свежими (`updatedAt = now`): пока канал жив, focus и повторное монтирование не делают запросов |
| `hello` / `heartbeat` | `version ≠ текущей` (пропуск, рестарт сервера) | resync |

Resync не запускается, если запрос snapshot уже идёт.

### Применение патча: `applyOrgTreePatch(queryClient, message)`

1. **Новый массив данных.** Изменённые узлы получают новые объекты `{ ...node, ...patch }`, остальные остаются теми же объектами.
2. **Метки массива.** Ему присваивается новая версия, и он помечается как «патченый»: собственный `structuralSharing` запроса сохраняет такой массив как есть, а обычные ответы сервера по-прежнему проходят через `replaceEqualDeep`.
3. **Модель.** Если модель для старого массива уже была посчитана, новая получается инкрементально (раздел 5) и регистрируется в кэше моделей для нового массива. Поэтому `select` не запускает полную агрегацию.
4. **Запись в кэш.** `queryClient.setQueryData`. Компоненты перерисовываются только там, где изменились ссылки.

## 5. Инкрементальный пересчёт: `updateOrgTreeModel(model, changedNodes)`

Задача: пересчитать агрегаты **только для затронутого узла и его предков**.

```
affected ← изменённые узлы ∪ все их предки (подъём по parentId)
для v в affected по убыванию level:                 # дети раньше родителей
    children' ← дети v, заменённые новыми версиями, если они в affected
    treeNode'(v) ← { node: новый или прежний узел, level, children' }
    stats'(v)    ← computeUnitStats(node, stats(children'))   # та же функция, что в полной агрегации
forest' ← корни, заменённые из affected
rows'   ← строки из affected получают новые итоги, остальные — прежние объекты
```

- **Стоимость:** O(|путь| · детей) на пересчёт статистик. Новые контейнеры `Map` и массивы копируют только ссылки.
- **Точность:** используются те же арифметические операции в том же порядке, что и в полной агрегации (`computeUnitStats`). Результат побитово совпадает с `buildOrgTreeModel` — тест сверяет модели после 200 случайных патчей через `toEqual`.
- **Сохранение ссылок:** узлы, строки и поддеревья вне пути остаются прежними объектами. Мемоизированные `OrgTreeItem` и `TableRow` вне пути не перерисовываются.

Пример: изменился `Core API` → пересчитываются `Core API`, `Платформа`, `Технологии`. Дивизион `Продажи`, ветка `Дизайн` и все их строки не трогаются.

## 6. AI-фильтр поиска

Ответ `POST /api/search/interpret` — `{ "filter": SearchFilter }`. Фильтр строит LLM по запросу на естественном языке, а применяется он **на клиенте** к строкам аналитической таблицы (`OrgTableRow`). Поэтому все числа относятся к тому, что видит пользователь: суммам по поддереву и взвешенной средней эффективности. Решение описано в [ADR-006](adr/006-ai-search-structured-filter.md), схема — в [`backend/docs/openapi.yml`](../backend/docs/openapi.yml) (`SearchFilter`).

```jsonc
{
  "nameContains": "платформ",        // string | null — подстрока названия (регистр и ё/е не важны)
  "levels": [2, 3],                   // (1 | 2 | 3)[] — дивизион / отдел / команда; [] — любой уровень
  "totalHeadcount": { "min": 5, "max": null },       // сотрудники поддерева, границы включительно
  "totalBudget": { "min": null, "max": 10000000 },   // бюджет поддерева, руб.
  "avgPerformance": { "min": 60, "max": null },      // 0–100
  "sort": { "key": "totalBudget", "direction": "desc" }, // | null; key — любой столбец таблицы
  "limit": 3                          // integer ≥ 1 | null — «топ N» по sort
}
```

Все поля обязательны (требование strict Structured Outputs): отсутствие условия выражается `null` или `[]`. Пустой фильтр (`EMPTY_SEARCH_FILTER`) пропускает все строки.

### Гарантии контракта

| Где | Что проверяется |
|---|---|
| OpenAI (strict JSON Schema, `search-filter.json-schema.ts`) | Форма, типы, `enum` уровней и ключей сортировки |
| Backend `parseSearchFilter` | Те же правила плюс нормализация: trim названия, пустое → `null`; уровни без дублей по возрастанию; `min > max` → обмен; эффективность обрезается до 0–100; отрицательные численность и бюджет, дробный или нулевой `limit` → ошибка → `502` |
| Client zod `searchFilterSchema` | Форма и диапазоны; нарушение → fallback на текстовый поиск |

### Применение: `applySearchFilter(rows, filter)` — O(n), при `limit` O(n log n)

1. Если условий нет, возвращается **тот же массив** `rows` (без лишних перерисовок).
2. Строка остаётся, если выполнены все условия: подстрока в `normalizeSearchText(name)`, уровень из `levels` (если не пуст), значения в диапазонах.
3. При `limit` строки сортируются по `filter.sort` (без него — в иерархическом порядке) и берутся первые `limit`. Это «топ N» по критерию запроса.
4. Затем таблица применяет **свою** сортировку. При применении фильтра она устанавливается равной `filter.sort`, пользователь может изменить её кликом по заголовку, не меняя выбранный топ.

Фильтр хранится как состояние, а не как отфильтрованный список, поэтому live-патчи (изменение сумм и эффективности) сразу пересчитывают выборку.
